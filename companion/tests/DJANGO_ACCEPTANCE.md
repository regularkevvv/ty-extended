The Django compatibility gate uses the existing django-ty source fixtures and
expectations without modifications. `scripts/django_acceptance.py` drives the
native Rust executable and the reference fork; Python does no source projection,
plugin execution, or type inference.

The gate checks:

- All 166 marked assertions across 38 dynamic features, including 49 model-ID
  cases. Every rejection must land on its original marked source line; unexpected
  diagnostics fail the gate. Reviewed diagnostic-message requirements are kept.
- Exact reference/native diagnostic codes, full messages, severity, original
  source paths and start/end positions, and process exit status.
- The existing e2e positive project and all six required negative controls.
- All 83 independent Django runtime proofs and nine QueryDict runtime/checker
  comparisons.
- All 18 supported Django/Python pairs from django-ty's checked-in version matrix.

`inventory` hashes the complete source fixtures and plugin package, including
stub markers and evaluator helpers, and records the matrix. Environment evidence
includes the interpreter hash, distribution versions, and hashes of installed
package files (excluding generated bytecode). `baseline` checks the original
fork against the unchanged expectations. `compare` adds the native companion and
requires the reference baseline to pass. An omitted runtime gate is recorded in
the report; a partial matrix cannot report complete compatibility.

Example, with absolute paths supplied by the caller:

```sh
python companion/scripts/django_acceptance.py compare \
  --django /path/to/django-ty \
  --output /tmp/django-acceptance \
  --fork /path/to/ty-extended-0.84.4 \
  --official /path/to/official-ty-0.0.84 \
  --companion /path/to/ty-companion-rust \
  --python /path/to/candidate-environment \
  --python-version 3.13
```

The existing plugin manifest supports ty-extended 0.84.4, which uses upstream
ty 0.0.84. The 0.86 fork already disagrees with the unchanged ModelForm inherited
`Meta` assertion; that upgrade failure must be recorded separately, never removed
from the compatibility corpus.

`scripts/django_matrix.py` prepares the exact declared Django versions and runs
the same gate for every Python version. `--interpreters` is a JSON mapping from
Python minor versions to interpreter paths. It verifies installed versions and
keeps mypy, django-stubs, django-stubs-ext, and pydantic-monty out of candidate
environments. Mypy comparison scores are not substituted for the official Django
contract.

Run `compare --reuse --checker-mode cli` and `compare --reuse --checker-mode push`
against the prepared matrix. Each mode writes a separate `compare-MODE.json`
summary and `evidence-MODE` directory for every pair; neither overwrites the
reference baseline. The full 18-pair matrix must pass in each tested mode.

`scripts/django_benchmark.py` times the unchanged conformance and both e2e
projects. It requires complete green acceptance reports from the exact binary,
source inputs, Python target, and dependency environment being measured:

```sh
python companion/scripts/django_benchmark.py \
  --django /path/to/django-ty \
  --output /tmp/django-benchmark \
  --fork /path/to/ty-extended-0.84.4 \
  --official /path/to/official-ty-0.0.84 \
  --companion /path/to/release/ty-companion-rust \
  --python /path/to/candidate-environment \
  --python-version 3.13 \
  --acceptance-cli /tmp/acceptance-cli/acceptance.json \
  --acceptance-push /tmp/acceptance-push/acceptance.json
```

The default is one first-observed run, two discarded warmups, and seven measured
repetitions per workload/backend, with backend order rotated by workload and fixed checker
parallelism. Each workload repeats the same backend order across repetitions. Every invocation, including warmups, must reproduce the complete
accepted diagnostic hash and exit status. Native projection/oracle/Monty counters
must remain equal across repeats. Original source positions and complete messages
remain part of the hash. A failed invocation stops the benchmark without a
successful timing summary.

Each invocation starts a fresh companion and official checker process. `push`
reuses the checker across projection rounds within that invocation. Repeated
invocations may benefit from OS filesystem caches; they are not a persistent warm
application, and the first observed run does not prove cold disk caches. Timing
includes subprocess startup and all native work, but excludes fixture preparation,
verification, and Python evidence writes. Native projection evidence writes remain
inside the measured process. Run on an otherwise idle machine; the report records
host load before and after each sample.

Keep `inputs.json`, `acceptance.json`, the matrix summary, command records,
diagnostic output, and source fixtures as evidence. Environments, downloaded
interpreter directories, uv caches, and extracted checker artifacts are generated
test dependencies and can be removed after the completed acceptance run.

For final generic runs, use `collect_evidence.py run-generic` to record binary,
fixture and source hashes before and after the unchanged Rust suite. Run all
three modes (`cli`, `lsp`, `push`) with the generic fixture's 0.86 checker pair:

```sh
python companion/scripts/collect_evidence.py run-generic \
  --companion /path/to/release/ty-companion-rust \
  --official /path/to/official-ty-0.0.86 \
  --fork /path/to/ty-extended-0.86.0 \
  --fixtures "$PWD/companion/tests/fixtures/generic" \
  --checker-mode push --output /tmp/final-generic-push
```

After every gate passes, `collect_evidence.py export` writes portable reports to
`companion/evidence` (the output directory must be new or empty):

```sh
python companion/scripts/collect_evidence.py export \
  --acceptance-root /tmp/django-acceptance \
  --companion /path/to/release/ty-companion-rust \
  --generic-cli /tmp/final-generic-cli \
  --generic-lsp /tmp/final-generic-lsp \
  --generic-push /tmp/final-generic-push \
  --unit-log /tmp/final-unit-tests.log --expected-unit-tests ACTUAL_COUNT \
  --protocol-log /tmp/final-protocol-tests.log \
  --benchmark /tmp/django-benchmark/benchmark.json
```

The acceptance root must contain `matrix/compare-cli.json` and
`matrix/compare-push.json`. Protocol replay must run both ignored tests with
`--nocapture` so actual request counts and response limits remain in the log.
Optional repeated `--supplemental-json LABEL=PATH` or
`--supplemental-log LABEL=PATH` arguments retain additional green gates without
inventing their counts. JSON must state a green outcome; supplemental Rust logs
must contain executed passing tests and no failed test/build result.

The exporter rejects partial matrices, missing gates, binary/source/dependency
mismatches and unverified benchmark samples. It retains complete normalized
diagnostics once per hash, all matrix cases and every benchmark sample/counter.
Temporary paths become explicit artifact labels. Unmodified originals and the
label mapping remain under the acceptance root; build trees and generated
projections are not copied into the branch.

Additional Rust gates use `cargo +1.98.0 test --release --manifest-path
companion/Cargo.toml`. Select the binary/tests and environment below. Integration
tests require `-- --ignored --nocapture`; use fresh output directories.

| Selection | Required environment |
| --- | --- |
| `--bin ty-companion-rust` | `TY_COMPANION_TEST_OFFICIAL` = official ty executable |
| `--test django_monty_parity` | `DJANGO_TY_SOURCE` = plugin checkout; `DJANGO_TY_ORACLE` = decompressed `evidence/protocol-inputs/oracle.jsonl.gz` |
| `--test django_frontend_edges` | `DJANGO_TY_SOURCE`, `TY_COMPANION_TEST_OFFICIAL`, `TY_COMPANION_TEST_FORK`, `TY_COMPANION_TEST_PYTHON` = Django environment, `TY_COMPANION_EDGE_OUTPUT` = fresh directory |
| `--test sdk_virtual_semantics` | `TY_COMPANION_TEST_OFFICIAL`, `TY_COMPANION_TEST_FORK`, `TY_COMPANION_SDK_OUTPUT` = fresh directory |

Use the 0.84 checker pair for these gates and `TY_MAX_PARALLELISM=1`. Harness
checks are `python3 -m unittest discover -s companion/tests -p 'test_*.py'`.
